# Управление VDBackup из ИИ-агента

VDBackup построен так, чтобы ИИ-ассистент или агент мог администрировать **всё** содержимое и
действия модуля без графического интерфейса, точно так же, как это делает человек через WebUI.
WebUI - это лишь один клиент небольшого JSON API; ваш агент - другой. Используйте API,
не скрапьте WebUI.

## Контракт

Всё проходит через одну точку входа, запускаемую от имени root на устройстве:

```
sh /data/adb/modules/vdbackup/scripts/helper.sh <verb> <base64(JSON-args)>
```

- Аргументы - это единый JSON-объект, **в кодировке base64**, передаваемый как один токен argv.
- Команда выводит **один JSON-объект** в stdout: `{"ok":true,...}` или
  `{"ok":false,"code":"ERR_...","message":"..."}`. Разбирайте его; никогда не скрапьте текст.
- Длительные операции (`backup`, `restore`, `import`) возвращают `{"ok":true,"opid":"..."}`
  немедленно и выполняются **отсоединённо** (они переживают исчезновение вызывающей стороны/WebUI).
  Опрашивайте их прогресс; они не завершены, когда вызов возвращается.
- `progress` и `cancel` принимают **base64 сырой строки opid**, а не JSON-объект.

Маленькая вспомогательная функция для вашей оболочки:

```sh
b64() { printf '%s' "$1" | base64 -w0; }
H=/data/adb/modules/vdbackup/scripts/helper.sh
sh "$H" backup "$(b64 '{"package":"com.example.app","mode":"full"}')"
```

Чтобы управлять этим с рабочей станции, выполняйте это через ваш обычный root-канал к устройству
(adb shell от имени root или конфигурация SSH-к-root). Модуль поставляется с встроенными бинарными файлами, поэтому
после установки ему **не нужен интернет** для локального резервного копирования/восстановления; только облачные
назначения (`rclone`/`restic`/ssh) обращаются к сети.

### Поля `progress`

Опрос `progress` возвращает актуальный `progress-<opid>.json` для операции. Эти поля
**всегда присутствуют**:

| Поле | Тип | Значение |
|------|-----|----------|
| `opid` | string | идентификатор операции |
| `percent` | int | завершённость 0-100 |
| `phase` | string | метка текущей фазы |
| `item` | string | тип текущего обрабатываемого элемента |
| `done` | bool | true при финальной записи (finish / dry-run / restore-test) |

Выполняющаяся операция может также нести эти **необязательные** актуальные поля. Они
отсутствуют или пусты, когда неизвестны, и **опускаются при финальных записях** (finish /
dry-run / restore-test):

| Поле | Тип | Значение |
|------|-----|----------|
| `rate` | string | скорость передачи, напр. `"4.2 MiB/s"` (пусто = неизвестно) |
| `eta` | string | оценочное оставшееся время, напр. `"1m12s"` (пусто = неизвестно) |
| `n` | int | индекс текущего элемента (0 = неизвестно) |
| `of` | int | общее число элементов (0 = неизвестно) |
| `cur` | string | имя текущего элемента (пусто = нет) |

Облачные передачи заполняют `rate`/`eta` (percent поступает из rclone); локальные Full-копии
заполняют `n`/`of`/`cur`. Метки фаз включают фазу запечатывания контрольной суммы
**`verified`** и, для облачных передач, **`transfer`** и **`mirror <item>`**.

### Аргументы `backup`

```json
{
  "package": "com.example.app",
  "user": 0,
  "mode": "full",                 // full | snapshot | mirror
  "compression": "zstd:10",       // none | lz4 | zstd[:N] | gzip
  "items": ["apk","data","data_de","obb","external","media"],
  "encrypt_data": false,
  "encrypt_apk": false,
  "dest": "local",                // local | <destination id>
  "verify": true,                 // re-hash each archive vs the manifest (default on for Full)
  "dry_run": false,               // true = report a size plan, write nothing
  "ssaid": false                  // OPT-IN, see below
}
```

`restore`/`import` принимают `{ref}` (каталог резервной копии / референс сканирования). `restore` также принимает:
`"items"` (подмножество типов элементов копии для восстановления; опустите для всех), `"test": true`
(извлечь во временный каталог и проверить, не затрагивая работающее приложение), `"mode"` для
snapshot/mirror, `"password"` для зашифрованной копии, `"ssaid"` (opt-in), и опции источника
установки `"spoof_installer"` (по умолчанию из config, задаёт установщиком Play Store во время
установки) и `"deep_spoof": true` (расширенный opt-in; также подделывает инициирующий пакет и
источник пакета, редактируя базу пакетов, применяется после перезагрузки). `import` принимает
`"from": "neo" | "databackup"` и, для зашифрованной резервной копии Neo, `"password"`.

### Аргументы `schedule-set`

Задание планировщика выбирает **одну** цель и **действие**:

```json
{
  "id": "nightly-games",
  "action": "backup",             // "backup" (по умолчанию) | "restore"
  "package": "com.example.app",   // одно приложение   - ИЛИ -
  "packages": ["com.a","com.b"],  // набор приложений   - ИЛИ -
  "all": true,                    // все приложения, кроме списка исключённых приложений
  "cron": "daily",                // hourly | daily | weekly
  "at": "02:30",                  // HH:MM
  "mode": "full",
  "dest": "local",
  "keep": 5,
  "items": ["apk","data"],
  "require_wifi": false,          // шлюз: запускать только по Wi-Fi
  "require_charging": false,      // шлюз: запускать только во время зарядки
  "min_battery": 0,               // шлюз: запускать только при заряде >= этого % (0-100)
  "days": [1,2,3,4,5]             // шлюз: запускать только в эти дни недели (0=воскресенье)
}
```

Укажите ровно **одно** из `package`, `packages` или `all` для цели. Задание `backup`
сохраняет обычные `mode`/`dest`/`keep`/`items`. Задание `restore` (`action: "restore"`)
восстанавливает **самую свежую** резервную копию каждого целевого приложения (или явный `ref`)
и **перезаписывает текущие данные приложения при каждом запуске** - это сделано намеренно и по
согласию (opt-in), поэтому задавайте это только по прямому запросу пользователя.

### Шлюзование планировщика

Запланированное задание может нести **необязательные условия-шлюзы**. Когда шлюз наступившего
задания не выполнен, оно **пропускается и повторяется на следующем тике, без продвижения своего
расписания** (его `last_run` не отмечается, поэтому оно срабатывает, как только условие
выполнится):

| Поле | Тип | Шлюз |
|------|-----|------|
| `require_wifi` | bool | запускать только при подключении к Wi-Fi |
| `require_charging` | bool | запускать только во время зарядки |
| `min_battery` | int (0-100) | запускать только при заряде не ниже этого уровня |
| `days` | array of int (0-6, 0=воскресенье) | запускать только в эти дни недели |

Поверх этого всегда применяется минимальная проверка **тепловой безопасности**: запланированная
операция пропускается, пока устройство критически перегрето. Каждый пропуск по шлюзу
записывается в журнал аудита как `op:"scheduler-gated"` с `reason`, равным `wifi` / `charging` /
`battery` / `days` / `thermal`.

### Аргументы `remote-add`

Облачное назначение - это назначение `type:"rclone"`, которое именует удалённое хранилище `rclone`; создайте
это удалённое хранилище сначала с помощью `remote-add`. `backend` может быть **любым бэкендом rclone** -
белого списка нет. `remote-add` принимает любое имя бэкенда (`dropbox`, `onedrive`, `box`, `pcloud`,
`mega`, `b2`, `s3`, `sftp`, `smb`, `webdav`, `ftp`, `drive` и ~70 других, поддерживаемых rclone), а
`params` передаются напрямую в конфигурацию `rclone` как пары `key=value`. Поля паролей хранятся
скрытыми, никогда в открытом виде. Распространённые бэкенды и их `params`:

```
sftp   : host, port, user, pass           smb  : host, port, user, pass
ftp    : host, port, user, pass           webdav: url, vendor, user, pass
s3     : provider, access_key_id, secret_access_key, endpoint, region
drive  : token, scope                     (token = output of `rclone authorize "drive"`)
```

**OAuth на устройстве (без ПК).** Бэкенды, требующие входа через браузер (Google Drive, Dropbox,
OneDrive, Box, pCloud), не требуют компьютера или вручную вставленного токена. Вызовите
`remote-authorize` с `{backend}`: движок запускает `rclone authorize <backend>` на локальном
сервере обратного вызова (`127.0.0.1:53682`) и открывает собственный браузер телефона на странице
согласия провайдера через Android VIEW-интент, возвращая `{ok:true,url}` (или
`{ok:false,code:"ERR_AUTHORIZE"}`). Опрашивайте `remote-authorize-poll` (`{}`): он возвращает
`{ok:true,done:false,url}` во время ожидания и `{ok:true,done:true,token}` после одобрения
пользователем - передайте этот `token` в `remote-add`. `remote-authorize-cancel` (`{}`)
останавливает ожидающую авторизацию (`{ok:true,cancelled:true}`). Ручная вставка вывода
`rclone authorize "<backend>"` с любого компьютера по-прежнему поддерживается как запасной вариант.

У Google Drive есть два пути: это удалённое хранилище `drive` (проект Google Cloud не нужен, использует
собственный OAuth rclone - авторизуйтесь на устройстве с помощью `remote-authorize`, или выполните
`rclone authorize "drive"` один раз на любом компьютере и передайте token) или опциональное
приложение-компаньон (ваш собственный OAuth client id). Оба в итоге становятся обычными назначениями.

### Сетевая политика

Поле конфигурации `network_policy` управляет тем, какое соединение могут использовать облачные передачи:
`any` (по умолчанию), `wifi` или `mobile`. Задайте его через `config-set`. Когда оно равно `wifi` или
`mobile`, каждая облачная передача (загрузка Full `rclone`/Drive, синхронизация Mirror, удалённое
резервное копирование/восстановление снимка `restic`, восстановление Mirror) сначала проверяет активный транспорт и
прерывается с `ERR_NET_POLICY`, если он не совпадает - как для ручных, так и для запланированных заданий.
Локальные назначения никогда не ограничиваются.

### Облачная целостность и квота

- **Запечатывание контрольной суммой (облако).** После успешного облачного копирования движок
  выполняет удалённую проверку контрольной суммы (`rclone check`); несовпадение завершает
  операцию с `ERR_VERIFY`. Бэкенды, не имеющие общего хеша с локальной стороной, пропускаются
  (это не сбой).
- **Проверка квоты (облако, режим Full).** Перед загрузкой в режиме Full в удалённое хранилище
  `rclone` движок запрашивает свободное место хранилища (`rclone about --json`) и отказывается с
  `ERR_QUOTA`, если резервная копия не поместится. Хранилища, не сообщающие сведений о квоте,
  пропускаются. Режим Mirror - это дельта-синхронизация и он освобождён от проверки.

### Облачные двоичные файлы (редакция `lite`)

Редакция `full` содержит все двоичные файлы во встроенном виде и никогда не нуждается в сети.
Редакция `lite` опускает два самых больших, `rclone` и `restic`, и загружает их по требованию при
первом запуске облачного или snapshot действия. `cloud-status` сообщает, присутствуют ли они уже,
может ли эта редакция их загрузить, и размер загрузки в байтах. `cloud-fetch` работает
**отсоединённо** (опрашивайте `progress` с его `opid`): он загружает дополнение `rclone`+`restic`
для конкретной архитектуры, проверяет его по SHA-256, вшитому в модуль, и устанавливает в кэш
времени выполнения. Его фазы прогресса - `downloading`, `verifying` и `installing`; итоговый код -
`ERR_NONE` при успехе или `ERR_FETCH` (загрузка не удалась) / `ERR_FETCH_VERIFY` (несовпадение
контрольной суммы, отброшено) при сбое. В редакции `full` он не нужен. `backup`/`restore` в
облачное или snapshot назначение в редакции `lite`, до того как двоичные файлы появятся,
завершается ошибкой `ERR_CLOUD_FETCHABLE`; клиенту следует предложить запустить `cloud-fetch`, а
затем повторить попытку.

### Категории особых резервных копий

`special-categories` сообщает, какие общесистемные категории есть у устройства; `special-backup`
захватывает те, что вы передаёте в `categories`, а `special-restore` применяет их заново.
Категории таковы:

| Категория | Что это | Семантика восстановления |
|-----------|---------|--------------------------|
| `messages` | SMS/MMS | замена в провайдере (очистка + извлечение) |
| `contacts` | контакты и журнал вызовов | замена в провайдере (очистка + извлечение) |
| `wifi` | сохранённые сети Wi-Fi | замена в провайдере (очистка + извлечение) |
| `bluetooth` | сопряжения Bluetooth | замена в провайдере (очистка + извлечение) |
| `calendar` | провайдер календаря (`com.android.providers.calendar`, приложение + данные); также переносимо экспортируется в `calendar.json` | замена в провайдере (очистка + извлечение) |
| `wallpaper` | обои главного экрана и экрана блокировки плюс `wallpaper_info.xml`, хранятся сырыми (в двоичном виде) | файлы заменяются |
| `dns` | режим и спецификатор приватного DNS, считанные из settings | идемпотентное `settings put` |
| `system_settings` | полный дамп настроек system/global/secure | **opt-in**, идемпотентное `settings put`, перезаписывает настройки устройства |

**`system_settings` строго opt-in и деструктивно при восстановлении.** Как и `ssaid`, оно
перезаписывает общесистемные настройки при восстановлении, поэтому защищено явным согласием
пользователя и записывается в журнал аудита. Никогда не выбирайте его по умолчанию; только по
прямому, осознанному запросу пользователя.

### Отдельная резервная копия пути

`path-backup` / `path-restore` создают резервную копию и восстанавливают **любой абсолютный
путь** - папку или один файл - в общем хранилище или под `/data`, вне модели по приложениям.
Архив записывается как `tar.zst` плюс `manifest.json` в собственном формате VDBackup
(запечатан SHA-256, с набором RECOVERY при шифровании) под `.paths/` в каталоге резервных копий.

```json
// path-backup
{ "path": "/sdcard/DCIM/Camera", "compression": "zstd:10", "password": "..." }
// path-restore
{ "ref": "<.paths ref>", "confirm": true, "password": "..." }
```

- Исходный путь должен быть **абсолютным** и находиться под одной из разрешённых roots:
  `/storage/emulated`, `/data/media`, `/sdcard`, `/data`. Несуществующий путь завершается
  ошибкой `ERR_NO_PATH`; путь вне разрешённых roots или содержащий `..` завершается ошибкой
  `ERR_BAD_PATH`.
- `path-restore` записывает обратно в исходное расположение, поэтому он деструктивен и требует
  `"confirm": true` - затвор с высоким трением, как у `special-restore`. `ref`, не являющийся
  действительной резервной копией пути, завершается ошибкой `ERR_BAD_REF`.
- Оба выполняются **отсоединённо**; опрашивайте `progress` с возвращённым `opid`.

### `update-check`

`update-check` сообщает, была ли опубликована более новая версия модуля, чтобы агент (или WebUI)
мог её показать. Это **глагол чтения, который возвращается сразу** - он **не** отсоединён, поэтому
нет `opid` для опроса. Запускается только явным действием пользователя и загружает опубликованный
манифест обновления модуля (URL `updateJson` из `module.prop`) с помощью встроенного `curl` через
HTTP-запрос со стороны root - это выполняется вне WebView, поэтому не подпадает под CSP WebUI - и
сравнивает опубликованный `versionCode` с установленным. Не принимает **никаких аргументов**.

В случае успеха возвращает:

| Поле | Тип | Значение |
|------|-----|----------|
| `ok` | bool | `true` |
| `current_version` | string | установленный versionName |
| `current_code` | int | установленный versionCode |
| `latest_version` | string | опубликованный versionName |
| `latest_code` | int | опубликованный versionCode |
| `update_available` | bool | `true`, когда `latest_code` больше `current_code` |
| `zipUrl` | string | URL опубликованного zip |
| `changelog` | string | URL опубликованного changelog |
| `notes` | string | примечания к выпуску |

Если URL `updateJson` отсутствует, сетевой запрос не удаётся, или манифест не удаётся разобрать,
возвращает `{"ok":false,"code":"ERR_UPDATE_CHECK"}`.

`update-check` только **сообщает** о доступности и примечаниях к выпуску; само обновление выполняет
ваш root-менеджер (KernelSU / APatch / Magisk) через `updateJson` модуля, а не этот глагол.

## Предохранители, которые ваш агент должен соблюдать

- **`ssaid` строго opt-in (по умолчанию выключен).** Он создаёт резервную копию / восстанавливает
  ANDROID_ID устройства, переписывая системный файл; восстановление применяется только после перезагрузки, и
  предыдущий файл всегда сохраняется сначала для отката. Отправляйте `"ssaid": true`
  только по прямому, осознанному запросу пользователя - никогда по умолчанию.
- **Мутирующие действия (restore, delete, import) являются деструктивными** и записываются в
  локальный журнал аудита (`logs/audit.jsonl`). Восстановление точное (стереть-затем-извлечь), поэтому
  оно возвращает приложение в точное состояние резервной копии. Подтверждайте намерение, прежде чем вызывать их.
- **`system_settings` opt-in и деструктивно, точно как `ssaid`.** Его восстановление
  перезаписывает общесистемные настройки, поэтому отправляйте его только по прямому запросу
  пользователя; оно защищено явным согласием и записывается в журнал аудита.
- **Восстановление идемпотентно.** Сырые восстановления провайдера (messages/contacts/wifi/
  bluetooth/calendar) **заменяют**, а не сливают - данные провайдера очищаются, и архив
  извлекается поверх них - поэтому повторное восстановление той же копии не может продублировать
  строки. `dns` и `system_settings` применяются заново идемпотентным `settings put`.
- **Извлечение архивов защищено от обхода пути (path traversal).** Восстановление выполняется от
  root, поэтому каждый архив (restore, import, special-restore, path-restore) проверяется перед
  любой записью: тот, чьи элементы используют абсолютные пути или содержат `..`, заранее
  отклоняется с `ERR_UNSAFE_ARCHIVE`, до того как произойдёт хоть одна деструктивная запись (GNU
  tar также запускается с `--no-absolute-names`). Подделанный архив никогда не может выйти за
  пределы своего целевого каталога.
- **Никогда не ослабляйте** сохранение (SELinux/uid/gid/режимы/xattr) или правило APK (APK
  всегда сжимаются, никогда не шифруются, если не задан `encrypt_apk`).
- Считайте вывод JSON источником истины; проверяйте `ok`/`code`, опрашивайте `progress`,
  и выводите коды `ERR_*` вместо того, чтобы гадать.
